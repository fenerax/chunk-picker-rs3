# How and Why performance — November 2026

START `c185bd7c932d96642506b10c3c0935fb689b7d02`. Branch `perf/p6-how`.

## Changes

- `app/tasks/worker.mjs`: give How the current resident list snapshot, when present. The wire protocol is unchanged.
- `app/tasks/engine.mjs`: weakly bind a stable processing closure to its conservative eligibility fingerprint. A matching How request runs the same fresh final capability pass with those admissions, then projects the asked row only. It retains the full proof capture and alternative ranking, including later cheaper witnesses and admission ordering. Cyclic/full-discovery results and missing, foreign or stale snapshots keep the discovery path.
- The small shared-engine edit also reuses unchanged access and resource collection within one proof capture. Captures never share evidence or memo entries. Ordinary evaluation uses its existing memo path.
- `tests/task-how.test.mjs`: complete START proof hashes for 47 public synthetic row/state pairs; snapshot/direct/cache equivalence; changed member/input and revision rebinding; processing chains, cyclic fallback, cancellation and output budgets.
- `scripts/perf/how-why.mjs`, `how-why-probe.mjs`, `how-why-summary.mjs`: calculator-only measurements, diagnostic spans and canonical comparisons. No private state or pack contents are embedded in these scripts.

## Method

Linux, Node `v24.21.0`, real packs, process workers, 5 fresh workers per side, serial execution. Each worker evaluates both members and opens 5 rows per member. Rows are selected by index: take the middle available, uncompleted row in 5 evenly spaced categories. The retained save is copied to temporary storage and read with filesystem reads, static-sidecar digest checks and state validation. No private server, normal store or credential creation is used.

The harness sends one full state and then snapshot references. An ordinary full evaluation warms each list snapshot. Each How is followed by an exact repeat and saved Why. Saved Why calls the HTTP helper directly over compressed calculator output. Browser downloads, network latency and the full-result supplement are not measured.

Each table entry is the median [min–max] of 5 fresh runs. Aggregate latency is the median of each trial’s median over its sampled rows, then the median [min–max] across the 5 trials. Instrumented diagnostic runs are separate and excluded from these timing and memory figures.

Canonical payloads sort object keys recursively, retain array order and omit only nondeterministic `elapsedMs`. They include the entire How/Why envelopes, graph IDs, admission order, wording, limits, gaps and assumptions. Other request types are unchanged; the changed request paths are evaluate and how-task. Saved Why is checked as a consumer of the evaluated result.

## Proof-stage diagnosis

The original path creates 2 eligibility generators per uncached How and resumes them 4 or 6 times, including recipe discovery and a fresh final pass. The verified-snapshot path creates and resumes 1 generator. In separate instrumented runs, fresh access calculations fall from 12 to 1 for one member and from 19 to 3 for the other. Source-collection calls fall from 12 to 4 and 19 to 5, with unchanged views memoized inside that capture. Proof finish is still called once.

Proof finish includes global alternative ranking and export. It remains intact: stopping at the first successful route or pruning by the first witness would lose later cheaper alternatives and change graph/admission IDs. The largest avoidable work was discovery plus the full catalogue’s display, equipment and result projection, rather than graph export.

## Remaining scope and risks

The How gain depends on a resident, matching list snapshot. Cold/evicted snapshots and cyclic closure fallback still perform discovery. One row’s median gain is below 1.5 s even though the aggregate target is met. The shared engine edit is limited to How replay/projection and binding its input metadata; ordinary full-result hashes match.

Why’s full-result supplement is not removed. Compact list rows omit authored records and calculated source/provenance fields needed for identical answers. The browser triggers the supplement in `app/web/screen-tasks.mjs` (`appendTaskWhy`/`ensureDuoDetails`) and `app/web/screen-loading.mjs` (`ensureFullResult`), outside the permitted P6 files. Removing avoidable requests needs that browser scope and corresponding tests; if richer list evidence is needed, `app/play-view.mjs` must also be authorized. No such files were changed.

The named `docs/perf/hotspots-2026-11.md`, `scripts/perf/hotspots-engine.mjs` and `scripts/perf/worker-wake.mjs` are absent at START. The new scoped harness replaces them for these measurements. No Rust, GitHub operations or private server validation are used.
