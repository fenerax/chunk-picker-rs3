# Picker footprint, Phase 0

The harness measures an installed save and a fresh one-member picker sequentially,
using the same pinned dataset/packs/profile/add-on. It does not estimate production
capacity from the included small fixture. No application code changes are needed.
Run with vanilla Node 24.20 or newer 24.x; there are no dependencies.

## Installed release on Linux

Use a stopped, coherent **scratch copy** of the matching backup store and its
sibling dataset receipt. Do not point this tool at a live writer. The source must
have no lock/recovery marker, symlinks or hardlinked files. The tool copies and
verifies the store before opening it, creates a fresh credential only in its own
private temporary copy, and removes that entire temporary tree on completion or
handled failure. It never opens the source as a writable store. Output must be a
new file outside the source and installed code tree. Allow temporary disk space
for the original copy plus four store-only copies per trial.

From the checkout containing the harness, replace `/scratch/backup-store` with
the prepared scratch store directory; retain its sibling
`/scratch/backup-store.dataset.json`:

```sh
systemd-run --scope -p MemoryMax=4G -p CPUWeight=20 \
  nice -n 19 node scripts/perf/picker-footprint.mjs \
  --pointer /opt/chunk-picker/releases/rel29-36b9db7/pointer.json \
  --store /scratch/backup-store --port 8990 \
  --max-rss-mib 3500 --out /scratch/picker-footprint-rel29.json
```

Use an absolute Node path if the scope environment does not resolve the intended
Node 24 installation. `--port` accepts 0 (an OS-assigned scratch listener) or
8900–8999. The listener is loopback-only. Port conflicts fail; the harness never
stops an existing service. It needs neither production network access nor
sign-in-provider secrets. External progress fetches are disabled.

`readRelease` verifies configuration/input pins and inventories the installed
code, then rechecks release identity after both trials. Only the scratch data
directory/listener and measurement controls differ from the pinned runtime.
Environment resolution follows `scripts/linux/runtime.mjs:32`: the Linux release
runtime explicitly selects **process-hosted calculators**, even though the raw
scheduler's platform default is threads (`app/tasks/scheduler.mjs:16`). The report
records `workerMode: 1` for process mode. Each host contains a calculator thread;
their RSS/CPU must not be counted twice.

The harness disables automatic prediction prewarming and startup warmup, and
sets a short worker idle interval (default 2,000 ms, configurable with
`--idle-ms`). These controls isolate foreground work and let sleep finish within
one trial. They do not represent production background job arrival rates. A cold
measurement includes calculator wake, imports/compilation, input transfer,
evaluation, serialization and HTTP response consumption. Each member is measured
after sleep clears calculator caches. The immediate identical full task request
is the warm repeat, which may be served by the normal retained result cache.
It is **not** a forced uncached warm-engine calculation.

The separate uncached full `/api/state` request evaluates all members' roll pools
on the HTTP event loop (`app/server.mjs:656`). It measures that current roll-pool
path, not speculative worker Preview batches or random-roll mutation. No earlier
state request fills its response cache.

## Local synthetic run

Create an empty scratch source outside the checkout. The included open-f2p app
will initialize its copied store; the original stays empty and unbound:

```sh
mkdir /tmp/picker-footprint-source
node scripts/perf/picker-footprint.mjs --app-dir "$PWD/app" \
  --store /tmp/picker-footprint-source --port 8990 \
  --out /tmp/picker-footprint-synthetic.json
node --test --test-timeout=120000 tests/picker-footprint.test.mjs
```

An app directory generated by `scripts/perf/scale-server.mjs` also works. The
focused test instead seeds a bound, two-member open-f2p store with one unlocked
starting chunk and a sentinel, and verifies its complete file inventory and
binding remain unchanged, including after a memory-budget refusal.

## Report interpretation

All leaf values are finite numbers; field names are fixed schema identifiers.
Members are zero-based indexes. There are no names, chunk/task IDs, paths,
credentials, response bodies, origins or machine names in the report.
`releaseIdUtf8` is the release directory basename encoded as UTF-8 bytes;
`datasetDigestBytes` is the 32-byte SHA-256 digest. `nodeVersion` is a numeric
major/minor/patch array; timestamps are Unix milliseconds. `linux` and `solo` are
0/1 flags. Linux-only unavailable measurements are zero on other platforms.

Each trial includes these measurements:

- `snapshots.beforeImport`, `afterImport`, `afterStoreOpen`, `idle` and `asleep`:
  main `process.memoryUsage()`, full V8 heap statistics, `cpuUsage()`,
  `threadCpuUsage()`, `resourceUsage()`, and Linux `/proc` VmRSS/VmHWM in bytes.
  `afterStoreOpen` captures the existing synchronous `create:store` startup log
  event through a harness-only preload; no installed file is modified.
- `evaluations`: cold/repeat wall time and CPU deltas for each indexed member.
  Main CPU covers the HTTP process; worker CPU totals sum relay hosts only,
  because host `cpuUsage()` includes the calculator thread. CPU units are
  microseconds; divide combined user+system totals by 1,000,000 for core-seconds.
- `series`: numeric samples from the main, each relay host and every calculator
  isolate at 100 ms intervals and at result sends. These retain process and
  thread CPU/resource/V8 records for independent analysis. Worker `workers`
  summaries include observed heap/RSS peaks and kernel VmHWM. VmHWM/maxRSS are
  lifetime peaks, not per-request peaks. Node resource `maxRSS` uses KiB;
  `memory.rss`, `proc.vmRSS`, and `proc.vmHWM` use bytes.
  `processTreePeakRSSBytes` is the separate supervisor's observed Linux tree peak
  (zero when unavailable), avoiding duplicate thread RSS.
- `contexts`: open one, then separately three additional copies with `openStore`
  in the same trial process and no scheduler/worker. After each GC, record total
  retained main heap delta and delta/count. Close the first batch before the
  three-context batch. The measured server is closed first to release its writer
  and make coherent copies; its handle, store and shared world stay reachable as
  the baseline. This isolates **store/state cost**, excluding sidecars, HTTP
  caches, subscribers and future account-registry overhead. Negative/noisy deltas
  are preserved rather than clamped to zero.
- `storeBytes` counts logical regular-file bytes in that trial's complete store;
  `bindingBytes` counts its sibling receipt separately. `sourceBytes` is the
  original copied store size before scratch credential/session and migration
  work. These are not filesystem allocated blocks or shared pack bytes.
- `initialProgress` confirms the fresh solo has one member, revision zero and
  zero inherited unlocked/completed progress. Solo uses `createGroupState` with
  one neutral owner; it never derives initial progress from the supplied store.

Synchronous evaluation blocks timer sampling within its isolate. Result-send
samples reduce that blind spot but worker heap peaks remain **observed lower
bounds**, not allocator-exact maxima. RSS is process-wide: relay and its worker
thread report the same process RSS. Sum one row per PID, never every thread row.
`resourceUsage()` is also process-wide; `threadCpuUsage()` identifies isolate
thread CPU. The supervising process is measurement overhead, outside trial RSS.
Sampling and synchronous sample-file writes add overhead to measured CPU/latency;
these figures have no uninstrumented control or overhead subtraction.
Series phase numbers are 0 for periodic/result samples, 1/2 before/after imports,
3 after store open, 4 after sleep, 5/6 before/after tasks, 7/8 before/after the
roll pool, and 9/10 before/after extra store contexts.

On Linux a separate supervisor checks the trial process tree every 50 ms, even
while application loops are busy. Above `--max-rss-mib` it terminates the trial,
with a force-kill fallback. A main-process guard also cancels in-flight startup
and requests. Sampling can overshoot between checks; the recommended cgroup
`MemoryMax=4G` supplies the OS hard ceiling, including supervisor overhead. No
success report is written after a budget breach. Windows local measurements have
only the main-process RSS guard; use Linux for process-tree capacity evidence.
