# Calculator wake, November 2026

Base: `c185bd7c932d96642506b10c3c0935fb689b7d02` (START).
Linux, Node 24.21.0, process workers. No server or normal store was opened on
the private input. The calculator harness reads and validates an explicitly
copied scratch state with ordinary filesystem reads. It creates no credentials.

## Method

`scripts/perf/worker-wake.mjs` runs five independent parent processes per cell,
one calculator at a time. Each parent loads the dataset and retains its initial
catalogues, completely retires the seed worker, then times a fresh replacement.
The two full task requests run in member-slot order. Both completion times are
relative to spawn; slot 2 includes slot 1's preceding work. Hashing happens after
timing and memory sampling. Hashes use the existing calculator comparator's
canonicalization, including removal of its documented volatile fields.

RSS is sampled every 25 ms from Linux `/proc` for the owned worker process
(relay and calculator thread together) and from the parent. Idle means two
seconds after both responses, with no forced GC. Peaks are sampled maxima, not
an exact allocator high-water mark. No tests or other calculators run alongside
these measurements. This host has a four-CPU quota and a 16 GiB memory limit;
it is not the six-vCPU production VPS.

Example (supply pack selection and defaults through the environment):

```sh
node scripts/perf/worker-wake.mjs --root /path/to/START \
  --data-dir /tmp/perfwalk/game --runs 5 --output /tmp/wake-before.json
node scripts/perf/worker-wake.mjs --root . \
  --data-dir /tmp/perfwalk/game --runs 5 --prepare --omit-ready \
  --output /tmp/wake-after.json
```

## Candidates

- Definition preparation: inherited stages already prevent the reviewed
  server corrections from running twice. The remaining parse/preparation costs
  176 ms [154–262]. Retain the ledger and its behavior.
- Collection preparation: an immutable V8 byte string replaces repeated
  drop expansion and identity construction: 1,681 ms [1,323–1,994] to build,
  versus 927 ms [674–1,561] for the first deserialize in each of five fresh
  workers. Serialization costs 461 ms [395–539] once, for 85,781,633 bytes.
  One entry serves the scheduler's native foreground calculator, capped at
  128 MiB. Advisory lanes rebuild normally so additional decoded graphs do not
  multiply across all lanes. It is
  keyed by dataset digest, definition bytes, dataset options, inherited stages,
  all application module sources, and Node/V8 versions. Checksum, key, read or
  deserialize failures fall back to an ordinary build. No saved-state input
  reaches preparation.
- In-memory handoff was rejected as the default. Five-run ready/list medians
  were 3.81/15.52 seconds: moving the 82 MiB preparation through wake IPC lost
  much of the construction saving. The scratch-file prototype instead measured
  2.88/13.15 seconds, with identical results. That justified a temporary file
  cache; the integrated implementation is measured separately below.
- Lazy geography: an engine variant used only for its identity catalogue no
  longer builds an access index. Preparation/evaluation builds the same index
  and entrance table and configures automatic transport before using either.
- Lazy collection: replacement handshakes need neither collection evaluation
  nor sandbox/derived identity sets. Restore those on first use, preserving the
  initial foreground's complete catalogue publication.
- Ready catalogue: native foreground replacements omit a catalogue once their
  lane owns its initial catalogue. The pooled scheduler already did this;
  advisory workers continue to omit it. Custom factories keep their input API.
- Dataset syntax validation: repeated syntax checks cost 709 ms [671–890]
  across 158,446,370 bytes in five fresh replacement workers. The main-thread
  provider now issues receipts bound to the dataset digest, environment, app
  sources and Node version. Workers still read/hash every file and check its
  exact path, size and hash against its receipt. Missing or stale receipts run
  the ordinary syntax check; the main thread always validates syntax. Existing
  gzip validation receipts and the ban on worker decompression are unchanged.
- A broader provider/values cache was dropped: parsing/decoding the generated
  values costs only 46 ms [44–63]. Retaining full provider inputs would add
  memory and another integrity boundary for little saving.
- Generated guide identities (69 ms [48–164]) and equipment catalogues
  (21 ms [15–35]) remain eager. Their small measured costs do not justify
  additional cache boundaries.
- Roll-world construction remains eager: 201 ms [169–491]. Its existing
  roll-pool behavior was kept in this change.
- Activity prewarm: inspected but not changed. Existing warm admissions reject
  sleeping/expired lanes; waking them earlier would change when memory becomes
  resident and would not reduce the measured spawn-to-response interval.
- Longer idle timeout: not changed. Its cost is keeping the measured idle
  worker RSS resident for each additional lane during the extra timeout.

## Correctness and validation

Preparation uses only definition/catalogue inputs. It never receives a player
state. The result/snapshot byte ledger is unchanged; the preparation cap is
separate and shared rather than multiplied by lane count. There are no native
compression streams or asynchronous cache writes to interrupt on retirement.

The new tests cover invalid keys/bytes/shapes, normal-build fallback, collection
catalogues and generator equivalence, lazy geography, owned-process reuse, and
foreground catalogue retention across idle retirement and coalesced wake.

## Cache operation

The default `RS3_WORKER_PREPARATION_MODE=file` uses a fresh `rs3-prepared-*`
directory beneath `RS3_WORKER_PREPARATION_DIR` (default: the OS temporary
directory). Only a complete, exclusively created, mode-0600 file is published
after rename. The parent passes its pinned byte count/checksum and preparation
key to a replacement; it does not keep or resend the large byte buffer.
The worker reads the file on first collection use and verifies it before
deserializing. Missing files, wrong keys, wrong sizes, corruption and read errors
all rebuild normally. A write error disables the cache for that scheduler.

`off` disables preparation; `memory` retains the measured IPC alternative for
diagnostics. Foreground and advisory allocation groups remain distinct in the
pool. Orderly close waits for an owned write before removing its private
directory. An unclean server exit may leave public cache bytes in the temporary
directory until OS/operator cleanup. Worker retirement never owns a cache
write, native compressor or decompressor.

## Before and after

Each entry is the median [minimum–maximum] of five fresh runs. The baseline is
untouched START; the candidate is `94b144f057a4e6b2794959ed6c73bea293c54eca`.
[Numeric measurements and validation receipts](wake-2026-11.json) contain
counts, hashes, sizes and durations only.

| Spawn → slot 1 list, seconds | 16.46 [15.29–31.41] | 14.39 [12.04–15.17] | −2.07 s |
| Spawn → slot 2 list, queued, seconds | 21.74 [20.46–36.99] | 19.92 [16.46–58.66] | −1.83 s |

| Combined idle RSS, MiB | 2257.7 [2241.7–2259.9] | 2336.7 [2327.9–2344.4] | +79.0 MiB |

| Worker peak RSS, MiB | 1660.8 [1526.7–1672.4] | 1652.2 [1639.3–1663.4] | −8.6 MiB |

The ready and first-returned-list medians clear the two-second target. The
second queued return gains 1.83 seconds and does not clear that threshold.
The combined idle increase is 79 MiB for the measured parent/foreground path;
advisory allocations receive no prepared graph. The cache occupies 81.8 MiB
of temporary file space. Filesystem cache/tmpfs charges are outside these RSS
figures; on tmpfs the file also consumes RAM. A disk-backed configured directory
avoids that extra tmpfs allocation.
These are calculator-only measurements, not a full-server/mixed-lane capacity
claim; the full six-vCPU/11-GiB deployment was not measured.

The startup-only ablations measured 3.01 s [2.75–4.03] to ready without a
collection cache and 5.02 s [4.79–8.48] with an in-memory preparation and full
ready payload. The in-memory preparation with ready omission measured
3.81 s [3.17–4.26]; its IPC cost made it a worse default than the file handoff.
The full-ready versus omitted comparison includes deferred collection work,
so it is not an isolated serialization-time estimate.

Cold seed readiness, using a separate five-run baseline startup cell, measured
6.82 s [5.72–7.25] before and 6.72 s [5.93–27.58] after. There is no claimed
median cold-start penalty or saving at this spread. The cache adds its one-time
serialization, transfer and file write to initial preparation. Cold-seed RSS
was not sampled. Timing variability was substantial: the 27.58-second cold
seed and 58.66-second queued response are retained, not discarded. The cold
outlier is close to the existing 30-second startup deadline.
