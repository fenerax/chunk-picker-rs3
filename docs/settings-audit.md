# Settings and feature audit

This is a source inventory and behavior comparison, not a claim of complete picker parity. It covers the retained upstream **6.9.68** (`reference/original-picker/index.js:1613`), its `reference/original-picker/modal.js` and `reference/original-picker/worker.js`, the declarative world export, and the authored `app/core`, `app/tasks`, and delivered `app/web` code on **2026-10-07**, with documentation and behavior metadata refreshed from source on **2026-10-08**. The delivered integration section records current source behavior. The original-settings table also retains the first-pass UI baseline for comparison. The behavior catalogue describes authored engine scopes; a saved checkbox or a passing metadata test does not prove upstream behavior.

## Current layout

The [23 unused original rule keys](kept-original-rules.md) are hidden in normal Chunk Rules use. Advanced collects them in one folded read-only group, while saves, original-picker sync and backups keep their values. The replaced Settings Task rules editor has been removed; Chunk Rules owns rule editing.

As of 2026-10-12, Settings has five sections: Map, Rolling, Tasks, Panels and Time estimates. The header identifies the player whose choices are being changed. Only the selected section appears; Find a setting searches across sections, including saved monster kill times. Clear or Escape returns to the selected section. The last section stays in this browser, with a fallback when browser storage is unavailable.

At widths up to 720px, the sections become a tap-in list with Back. Each setting has a short label, a plain help line and its control on the right. Theme stays in sync with More. Starting flag opens the existing editor; Map display closes Settings and opens the map panel, which owns chunk IDs, visibility, border/sticker colours and browser-local sizes. Rolling links to the shared Chunk Rules dialog.

Advanced is a validated personal preference, off by default, saved through the existing set-preference command with History, Undo and backups. It reveals calculation timings and JSON, raw History commands and archived restore history, migration/replacement reports, rule support/source details, saved settings or rules with no effect yet, and IDs or catalogue diagnostics in Info, BiS, travel, imports and map icons. Gameplay controls, known sources and unknown time estimates remain available. View-only links never offer Settings or Advanced diagnostics. Nothing is removed from the save.

The copied-save browser review covers all five sections at 1440px and 390px in dark, gray and light, with no horizontal overflow, plus search/Escape, remembered sections, theme synchronization, Advanced History and dialog handoffs. See [wording.md](wording.md) for the wording changes. Final checks: 642/642 targeted tests passed; the full `npm test` run through `.local/with-heavy.ps1` passed 2,510 tests with zero failures and one skip (2,511 total). The browser checks also ran through the shared lock; both copied-save servers and isolated browsers were stopped. Existing preference IDs, gameplay command behavior and per-player storage remain unchanged apart from the new Advanced preference.

## Inventory and authority

The original source defines **27 top-level settings**, **4 nested neighbor options**, **6 setting categories**, **136 default rule entries**, **134 rule descriptions**, **20 rule categories**, **3 presets**, and **35 task-generating rule flags**. The union of defaults, descriptions, structure, presets, task-generating flags and direct literal `rules[...]` references in `reference/original-picker/index.js` / `reference/original-picker/worker.js` contains **152 distinct rule IDs**. This includes dormant and historical names; they are retained for completeness, not automatically activated. The authored catalogue adds Rare Drop Inclusive, Secondary Primary Inclusive, House storage tasks and Non-permanent BiS, making 156 IDs without changing retained declarations. The metadata lives in `app/data/settings.mjs` and was extracted by a strict data-literal parser, with no network request or original application execution. `tests/settings.test.mjs` compares every exported source declaration with the retained source.

Three value domains must stay separate:

- **Original initializer defaults:** the historical `rules` literal mostly starts false; the three threshold/amount values are strings. These are not the duo’s saved rules. Some IDs in descriptions, structure or code have no initializer default.
- **Imported player rules:** migration copies primitive map rule values into each member’s `taskRules` while retaining the original map as provenance. Explicit member values override shared task-rule values. Do not populate absent keys with historical defaults: authored rule checks often treat absence as enabled.
- **Authored group rules:** `state.rules` is validated against `createRuleRegistry()`. It owns shared access, the rolling candidate pool and completion scope. `content.f2p` overrides the legacy `F2P` key for eligibility.

Before gameplay migration, the authored task pipeline reads retained map rules below shared and member task-rule overrides. After migration, the engine, presentation and equipment modules all omit retained map rules. Converted imports populate member rules; clearing converted profile flags no longer resurrects the retained payload. `set-task-rule` accepts any primitive key/value; backend acceptance is not a capability test. A UI should show an explicit inherited state for absent values and distinguish source defaults from effective player values.

## Rule behavior classification

The current 156-row catalogue contains **47 implemented-scope**, **76 category-gate**, **10 partial** and **23 retained-only** entries, counted from taskRuleDefinitions/taskRuleBehavior after the October 8 metadata refresh. These counts describe consumer types, not a percentage of original feature parity. The generated-task implementations are now scoped consumers; retained-only controls remain disabled.

- **implemented-scope:** an authored consumer implements the specific behavior described in the final column. This does not assert all original special cases.
- **category-gate:** the flag gates declared task rows carrying that exact Category tag. It does not establish original dynamic task synthesis, source expansion, ranking or UI parity. Counts are the full declarative catalogue, not available tasks on either private map.
- **partial:** a material limitation or different authority exists.
- **not-implemented:** the requested generated-task or ranking behavior has no authored implementation.
- **retained-only:** no authored direct consumer or matching declared Category tag was found. Keeping or editing the value cannot be called functional support.

Known material omissions include exact crafted-item override; exact skiller and secondary MTA behavior; unverified weight rows and coupled weight ranking; combat set effects; Diary/category gating and boost-formula differences; arbitrary XP reward allocation; and several dynamic special-source resolvers. The four collection generators now have scoped consumers and worker wiring, with independent semantic tests; this does not establish every original special-source route. Unknown hard metadata and aliases fail closed instead of producing invented eligibility. The authored coupled scorer implements ordinary weapon/shield/ammunition comparisons; the older `presentation.mjs` selector’s standalone limitation text must not describe the full equipment pipeline.

### Numeric threshold bug found during this audit

Upstream uses a tiny positive zero sentinel and inconsistent primary equality. The October 7 rules follow-up uses one parser/comparison helper across access, collections, task outputs, Activity Info and equipment (including ordinary consumables). Bare amounts are always denominators: 2.5 means 1/2.5, and 0.5 means 1/0.5 = 2; explicit fractions are probabilities. Zero includes every known rate. Unknown rates pass rarity but never classify as primary, and source panels retain their raw labels. Nested skill-output rates compose along the path. Invalid saved values remain preserved with diagnostics and evaluate using defaults.

Rare Drop Inclusive is a boolean defaulting false; Secondary Primary Inclusive is a boolean defaulting true for the duo’s cutoff house rule. The Settings panel places each checkbox directly under its amount and supports inherited values/reset. Equality uses the shared floating-point tolerance documented in [access-logic.md](access-logic.md). These two authored controls are implemented-scope additions, not original defaults. House storage tasks is an additional off-by-default generator with sourced post-rework buildability gates; Non-permanent BiS defaults on and filters temporary or dust-degrading equipment when disabled. Neither changes the retained original declarations.

Boss drops from the picker’s boss list count as item sources; turning it off removes those drops as sources but does not stop killing or training on bosses, Kill X Boss goals or boss collection-log tasks. Exact retained list membership and independent task/source gates remain in force.

The October 8 review covers 35 enabled rule IDs. Moving Show Diary Tasks, BIS Skilling and Boosting to partial yields **12 implemented-scope, 15 category-gate, 5 partial and 3 retained-only**, replacing the earlier 15/15/2/3 metadata classification for that subset. Achievement and historical lowercase Cleaning herbs remain retained-only; the capitalized Cleaning Herbs display control is implemented separately. These totals describe source-reviewed scopes rather than captured task matches or operational readiness. Relic energy/loadout optimization remains an additional planning limit; no equivalent original optimizer is established.

## Current BiS and Activity Info parity requirements

`reference/original-picker/modal.js:176–191` provides shells; the actual features are in `reference/original-picker/index.js:9364–9800` and `reference/original-picker/index.js:10467–10489`. A new button alone does not restore the original window.

**Current BiS:** style tabs for Melee, Ranged, Magic and Necromancy; optional Prayer, Tank, weight reducing, separate Stab/Slash/Crush; main hand/off-hand/shield/2h/ammunition comparison flags; slots from head through pocket; only-already-obtained filtering; prayer bonus; source lookup; per-slot upgrade chart; manually declared miscellaneous equipment. The authored equipment result already exposes selected loadouts, recommendations, alternatives and explanation/requirements/source fields. Missing specialized ranking must be named in the window. Shared source access and shared challenge satisfaction do not prove personal item ownership or equipment.

**Activity Info:** Skills, Quests, Diaries, Slayer and Clues tabs. Skills show highest available task, boosting-adjusted level, primary training methods, optional all intermediate tasks and checkmarks, passive skill editing and manual primary-method overrides. Quests show start/completion progress and steps; Diaries show achievement/tier progress, rule-controlled hiding and score; Slayer shows possible masters/tasks and level restrictions; Clues show doable steps. Original clue support is itself marked incomplete. Authored `result.training`, task rows, access, points and diagnostics supply reusable facts, but a generic raw JSON calculation popup was not an equivalent Activity Info window.

**Behavior verification:** use synthetic portable fixtures for metadata, command behavior and model changes, then inspect the delivered Settings / Current BiS / Activity Info surfaces. Persist/reload preferences; exercise inherited versus explicit task rules; check disabled/limited controls; preserve member-specific provenance and personal progress; avoid treating a shared obtain task as another member’s inventory fact. No private saved duo state was mutated to build this audit.
